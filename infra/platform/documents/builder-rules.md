# Builder rules (BOSS dev pod) — read fully before the first command

You are a builder on the BOSS cluster dev pod, in your OWN git worktree (an isolated copy; never cd to /work/boss or another worktree). Your brief precedes this document in the prompt: the packet verbatim from the system of record and the gate's invariants, derived from the files that decide them. Read it first and follow the invariants section literally. Your run has a packet of its own (its id closes the prompt): export it as `BOSS_AGENT_RUN=<run id>` in the shell you gate from, so the gate-run records which run launched it and the run lands on the green by itself.

1. Base and branch. `git fetch origin` then branch from `origin/main`: `git checkout -b <branch> origin/main`. (If origin/main moves while you build, the brief's base check `merge-base --is-ancestor origin/main HEAD` will fail right before the gate — expected; `boss gate --rebase` replays your commit onto the new main and the rebased sha is the one to report.) Branch name `fix/...` or `feat/...`, lowercase, hyphenated, a sentence-like title. Never `git rebase`. Never force-push. If origin/main moves under you, do not worry — the conductor merges cars; only re-base by `git checkout -b <branch>-2 origin/main && git cherry-pick <sha>` if asked.
2. Cargo ONLY through `wt-cargo` (on PATH): `wt-cargo test -p <crate> ...`, `wt-cargo clippy -p <crate> --all-features --tests -- -D warnings`, `wt-cargo fmt -p <crate>` (or `cargo fmt -p <crate>` — fmt is fine bare). It gives this worktree its own target dir, bounds jobs (4-wide and nice'd for a builder worktree — the pod is shared with the operator's interactive session, and it lagged when three builds collided) and never pass WT_JOBS yourself; bare `cargo build/test` can take the pod's 16 GiB / 8-CPU cgroup to its ceiling and kill other work.
3. TDD: write the failing test first, run it and SEE it fail, then the smallest change that makes it pass. Tests go beside the code (`#[cfg(test)]`) or in `crates/core/boss-testing/tests/` for shell/infra; use `boss_testing::repo_root()` and `boss_testing::scratch_dir(...)` — never a fixed /tmp path, never your own repo-root helper (a lint refuses both).
4. Before pushing, IN THIS ORDER: `cargo fmt` FIRST, then `git add`, then commit (a builder ran add, then fmt, then commit -F and committed the stale staging — one extra commit on the car, 2026-09-18); clippy as above on the crates you touched, the touched crates' WHOLE test suite with `--all-features` (`wt-cargo test -p <crate> --all-features` — `--lib` or a named test misses the `postgres`-feature integration tests, which redded two gates on 2026-09-15), then `bash infra/gate.sh --quick` (~15 s; must end "clean").
5. Commit: imperative mood title, a body that says WHY with the measured evidence from the packet, and end the message with exactly this line:
   Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>
6. Push: `git push origin HEAD:<branch>`.
7. Gate. Write the FULL gate command into a script in YOUR scratch dir (given in the prompt) as `gate.sh`, then run `bash <that script> > <your scratch dir>/gate.log 2>&1` in the FOREGROUND — never pipe it through tail, which hides the launch line until exit (the harness refuses inline command text containing the word git; a background task gets killed under memory pressure — the gate itself continues in-cluster either way, and auto-park is stamped at launch). The command:
   cd <your worktree> && export BOSS_AGENT_RUN=<your run id> && exec boss gate <branch> --wait --mode auto --rebase --park-backlog-item <FULL uuid of your packet, copied from the brief, never typed from memory> --park-summary '<what changed and why, 3-6 sentences, no backticks>' --park-excludes '<what this car deliberately does not do>' --park-test '<the tests and checks you ran, by name, with counts>' --park-verified '<what an operator would observe after landing>' --park-probe '<shell text>' --park-expect '<the exact string the probe prints on success>'
   Prose rules: single quotes, NO backticks anywhere (argv eats them), no double quotes inside except escaped within the probe.
   Probe rules: it runs later ON THE FORGE HOST as user david, cwd = the converged checkout of main, with a 60 s timeout. Available there: git (use `git show HEAD:<path>` to read the converged tree — never fetch), jq, curl, and `boss-sor-read "<api path>"` which prints the system-of-record JSON body for a GET. Not available: boss, kubectl, boss-api, cargo. Exit 0 and print the expect string when the claim holds; `exit 75` with a "not yet: ..." line when it cannot be judged yet (e.g. the change has not converged, or the event it needs has not happened); exit 1 when it is judged false. Guard every numeric test against null/empty (jq `// empty`, or `case "$x" in ''|*[!0-9]*) ... exit 75;; esac`; the quote-free form is `case ${n:-empty} in empty|*[!0-9]*)` — never prefix with a letter like `x$n`, which makes the guard match every digit and the probe read not-yet on both legs). grep is line-based: never grep for a phrase that wraps across lines in the source. REHEARSE the probe twice before launching: against your branch (it must print the expect string, exit 0) AND against origin/main (`git show origin/main:<file> | grep …` — it must NOT pass there; a pattern that is a substring of something already on main proves nothing). For a probe reading the live jobs API with a NEW query parameter, add a control leg: a key/value nothing matches must answer 0, else exit 75 (an old server ignores unknown params and answers the unfiltered count).
8. When the gate is launched (the script prints `boss gate: packet <id> branch <branch>@<sha>`), you may keep waiting up to ~12 minutes in the foreground; whether it finishes or not, STOP and report: packet id (full), branch, commit sha, gate packet id, files changed, tests added, and anything you observed that is worth a follow-up item (do NOT file items yourself). The operator resumes you if the gate goes red. Your report is recorded on your run's `reported` step once the gate is green; the run lands on it.
9. Do not: touch files outside your worktree; write to the jobs API except via `boss gate`; run kubectl mutations; read or print /etc/boss-train/forge.token or any credential; run a full `infra/gate.sh` (only `--quick`); start background tasks.
10. Web work in a worktree: the worktree has no node_modules. For svelte-check and mocked specs, symlink the operator's: `ln -s /work/boss/node_modules node_modules; ln -s /work/boss/apps/web/node_modules apps/web/node_modules; ln -s /work/boss/libs/web-kit/node_modules libs/web-kit/node_modules` (all gitignored). `bun test src/…` works without them for most files.
11. Svelte 5: never name a prop or local `state`, `derived`, `effect` or `props` — it shadows the rune and svelte-check reports a store misuse three lines from the cause (cost a builder 2 min on 2026-09-15).
12. Shell under `set -o pipefail`: never `… | head` or `… | grep -q` with a producer that keeps writing — SIGPIPE makes a random red (the no-producer-coin pin refuses it; it caught four lines in one builder's first draft, 2026-09-18). Make `head`/`grep` the producer or drain the pipe with `tr`/`cat`.
13. Keep the change small and the diff only your files. Match the surrounding comment density and voice (comments say WHY with dates and packet ids, as the codebase does).
