# Builder rules (BOSS dev pod) — read fully before the first command

You are a builder on the BOSS cluster dev pod, in your OWN git worktree (an isolated copy; never cd to /work/boss or another worktree). Your brief precedes this document in the prompt: the packet verbatim from the system of record and the gate's invariants, derived from the files that decide them. Read it first and follow the invariants section literally. IF your prompt ends with a `== THE RUN ==` section, your run has a packet of its own and that section carries its id: export it as `BOSS_AGENT_RUN=<run id>` in the shell you gate from, so the gate-run records which run launched it and the run lands on the green by itself. IF THERE IS NO SUCH SECTION you were briefed without a run — `boss brief` does not create one and cannot know one — so there is nothing to export and the placeholder above is not something to substitute. Three builders read this as unconditional, exported nothing, and their runs would have aged into `died` with their cars green (backlog c8703bee); the gate now warns when a car is parked and no run claims it.

0. Shell shape — this comes before every rule that shows a command. In an isolated worktree the harness's guard refuses, as too complex to verify: a heredoc (`cat > file <<EOF`, a `python3` heredoc, and any command written after one), a compound command that names git or loops over `boss-api`, and `$((...))` arithmetic in a loop. Measured across the builders of 2026-09-23 (runs 27bfbdac, 2c623d2e, 161944b2 and others), each of which rediscovered the same way round it, which is this rule: anything longer than ONE plain command — a chain, a loop, a pipe out of git, a commit message, a probe — is written with the Write tool into your scratch dir and run by absolute path, `bash <your scratch dir>/<name>.sh > <your scratch dir>/<name>.log 2>&1`, which always passes; read the exit status the tool reports, then the log. Edit files with the Edit and Write tools, never with a heredoc or an inline script. Every command the rules below show is one plain command per call or a script you wrote first, and the pin `builder_rules_run_every_compound_command_as_a_script` holds them to that (backlog 68535488).
1. Base and branch. `git fetch origin` then branch from `origin/main`: `git checkout -b <branch> origin/main`. (If origin/main moves while you build, the base check quoted at the end of this rule will fail right before the gate — expected; `boss gate --rebase` replays your commit onto the new main and the rebased sha is the one to report.) Branch name `fix/...` or `feat/...`, lowercase, hyphenated, a sentence-like title. Never `git rebase`. Never force-push. If origin/main moves under you, do not worry — the conductor merges cars; only re-base if asked, and then as two plain commands (rule 0): `git checkout -b <branch>-2 origin/main`, then `git cherry-pick <sha>`. Never `git reset --soft origin/main` to squash: worktrees share remote-tracking refs, so origin/main can move under you mid-build (another session's fetch), and the reset then folds the OTHER train's landed work into your commit as a reversal (it happened to the builder of 1b52c278, 2026-09-19, and was caught only by the diff read before push). Commit on the branch and let `boss gate --rebase` replay it, or cherry-pick onto a fresh branch cut from the origin/main you just fetched — and run the base check before pushing: the diff must be only your files. It is not restated here — these are the `base check` invariant's own lines, quoted from the one place that defines them, because the same sentence was corrected in this rule and in that invariant on one day by two builders who did not know about each other (8d054cb2 and 9843aeb9, 2026-09-19; backlog 395d24ad):

Three dots, because that diffs from the MERGE-BASE — the two-dot form compares the two tips, so every commit that lands on main while you build is reported back as your branch's deletions (on car 6e738252, one commit behind, two-dot said 47 files / 5235 deletions and three-dot said 7 files / 16 deletions — the builder's own files, 2026-09-19). Do not "simplify" it back: the false alarm invites the merge-or-reset this same rule forbids, and the three-dot form still catches the 1b52c278 case, because work folded into your OWN commit as a reversal shows up in the merge-base diff.

3. TDD: write the failing test first, run it and SEE it fail, then the smallest change that makes it pass. Tests go beside the code (`#[cfg(test)]`) or in `crates/core/boss-testing/tests/` for shell/infra; use `boss_testing::repo_root()` and `boss_testing::scratch_dir(...)` — never a fixed /tmp path, never your own repo-root helper (a lint refuses both).
4. Before pushing, IN THIS ORDER: `cargo fmt` FIRST, then `git add`, then commit (a builder ran add, then fmt, then commit -F and committed the stale staging — one extra commit on the car, 2026-09-18); clippy as above on the crates you touched, the touched crates' WHOLE test suite with `--all-features` (`wt-cargo test -p <crate> --all-features` — `--lib` or a named test misses the `postgres`-feature integration tests, which redded two gates on 2026-09-15), then the pre-flight door, which is not restated here — CLAUDE.md §Doors decides which mode it is, and it moved from `--quick` to the stronger one on 2026-09-21 while this rule went on naming `--quick` for a day (backlog 5d919334):

A change under infra/lint/, infra/forge/, infra/ops/, infra/dev/ or infra/platform/ is pinned by crates/core/boss-testing — the tests there drive those scripts on the real bundle — so a lint- or infra-only car that touches no Rust crate still runs that crate's whole suite before pushing, `wt-cargo test -p boss-testing --all-features`, the same as a touched crate (the builder of 1b847556 read "the touched crates' whole suite" as none, ran only the two lint-exercising tests, and its first gate went red, 2026-09-19). A WHOLE-CRATE SUITE CAN OUTLAST THE TEN-MINUTE WINDOW ONE TOOL CALL GETS, and a run cut off there is the shape of a green one: no failure, and no final `test result:` line. Measured 2026-09-22 — `wt-cargo test -p boss-jobs --all-features` reaches 148 test binaries in 11m20s; at ten minutes it had printed 125 `Running` lines and the eleven binaries sorting at or after `waiting_on_pg.rs` had not run, so a car was reported green and went to the gate twice on stale one-line expectations in two of them. wt-cargo now prints how many test binaries the run must reach BEFORE it starts: count the `Running` lines against that number, and a short count, or a missing final `test result:` line, is a run that did not finish — not a pass (backlog 3566f5b4). Redirect the suite to a file under your scratch dir and read its exit status the way rule 16 asks of the pre-flight.

6. Push: `git push origin HEAD:<branch>`.
7. Gate. Your own files — commit message, probe rehearsal, gate script, logs — live in YOUR scratch dir, which is the working directory THE RUN names (a directory of the run's own under the scratchpad, derived from its id) — or, briefed without a run, scratchpad/builders/<packet id>/ — and never at the scratchpad root: the root is shared by every run a session launches. One builder's commit-msg.txt was overwritten by another's mid-session (0f2ecbda, 2026-09-19), and two parallel runs that were never told a directory wrote the same generic names there, so one filed five items carrying the other's content (backlog dd747b4c, 2026-09-24). Write the FULL gate command with the Write tool into a script there as `gate.sh` (rule 0), then run `bash <that script> > <your scratch dir>/gate.log 2>&1` in the FOREGROUND — never pipe it through tail, which hides the launch line until exit (the harness refuses inline command text containing the word git; a background task gets killed under memory pressure — the gate itself continues in-cluster either way, and auto-park is stamped at launch). The command:
   cd <your worktree> && export BOSS_AGENT_RUN=<your run id> && exec boss gate <branch> --wait --mode auto --rebase --park-backlog-item <FULL uuid of your packet, copied from the brief, never typed from memory> --park-summary '<what changed and why, 3-6 sentences, no backticks>' --park-excludes '<what this car deliberately does not do>' --park-test '<the tests and checks you ran, by name, with counts>' --park-verified '<what an operator would observe after landing>' --park-probe '<shell text>' --park-expect '<the exact string the probe prints on success>'
   Item answer: `--park-backlog-item` in that template is ONE ARM of a choice the gate will not launch without, and it is the ordinary arm — your packet is the item this car builds, and the item closes when the car lands. Pass exactly one of: `--park-backlog-item <FULL uuid>` for that; `--park-design <the design-doc's FULL uuid>` when you were dispatched onto a design's plan and this car completes it (the gate reads the item off the design's `answers` edge); `--park-partial-item <FULL uuid>` for every car of a multi-car plan but the last, so the item stays open for its other pieces; `--park-no-item '<reason>'` when the car answers no item at all. `boss gate --help` is where each one's meaning is defined. Nothing records which cars make up a design's plan, so no check stops the closing arm landing on the wrong car of one — which car is last is yours to say (0906495a: this rule named only the first arm, and the refusal that had named the others at `boss car open` correctly lost them in 19a2aca3, leaving no path to `--park-design`).
   Prose rules: SINGLE quotes — a backtick inside single quotes arrives intact, while double quotes let the shell run it and record a hole (2376b89e) — and no double quotes inside except escaped within the probe. Or keep the shell out entirely: write the six texts to park.toml beside gate.sh (summary, excludes, test, verified, probe, expect, each a TOML literal string, with a triple-single-quoted block for a multi-line probe) and pass --park-file <that path> in place of the six --park-* prose flags; the item flag stays a flag (6f1e9b99).
   Probe rules: it runs later ON THE FORGE HOST as user david, cwd = the converged checkout of main, with a 60 s timeout. Available there: git (use `git show HEAD:<path>` to read the converged tree — never fetch), jq, curl, `boss-sor-read "<api path>"` which prints the system-of-record JSON body for a GET, and the tree's own `boss` CLI (installed from the converged image on every tick since 2026-09-18 — read-only: a probe proves, it never writes, and the unattended door gives it no BOSS_ACTOR so a write refuses itself). What is NOT available is the list in `infra/forge/host-absent-tools.txt`, and that file is the one to read rather than a copy here: `boss gate --park-probe` refuses against it, at gate time on your terminal rather than hours later as an exit code on a car, and it carries the reasoning and the measurement date for every entry. This paragraph used to restate it and went stale — it said `boss` was unavailable for the whole day after the forge started installing it (785dc91a). Exit 0 and print the expect string when the claim holds; `exit 75` with a "not yet: ..." line when it cannot be judged yet (e.g. the change has not converged, or the event it needs has not happened); exit 1 when it is judged false. Guard every numeric test against null/empty (jq `// empty`, or `case "$x" in ''|*[!0-9]*) ... exit 75;; esac`; the quote-free form is `case ${n:-empty} in empty|*[!0-9]*)` — never prefix with a letter like `x$n`, which makes the guard match every digit and the probe read not-yet on both legs). A probe that asks whether its qualifying event happened AFTER the change landed dates that cutoff from `$BOSS_CAR_CONVERGED_AT` — the commit time of this car's own merge, handed to every recorded probe and FIXED — never from `git log -1 --format=%ct HEAD`, which is the converged checkout's current head and advances with every train (~28 a day), so the car starves: three cars were measured unprovable that way on 2026-09-19 (a92571a6). Guard it first: `case ${since:-empty} in empty|*[!0-9]*) echo 'not yet: this car has not converged here'; exit 75;; esac`. grep is line-based: never grep for a phrase that wraps across lines in the source. REHEARSE the probe twice before launching: against your branch (it must print the expect string, exit 0) — write the probe text to `probe.sh` in YOUR scratch dir and run `bash <scratch>/probe.sh > <scratch>/probe.log 2>&1`, then read the log, because the worktree guard refuses `bash -c '<probe>'` whenever the probe names git, which a `git show HEAD:` probe always does (measured in an isolated builder 2026-09-23, backlog ff56cc00) — AND against origin/main: the same probe with `origin/main:` in place of `HEAD:`, written as `probe-main.sh` beside it and run by path the same way — it must NOT pass there; a pattern that is a substring of something already on main proves nothing). For a probe reading the live jobs API with a NEW query parameter, add a control leg: a key/value nothing matches must answer 0, else exit 75 (an old server ignores unknown params and answers the unfiltered count).
8. When the gate is launched (the script prints `boss gate: packet <id> branch <branch>@<sha>`), you may keep waiting up to ~12 minutes in the foreground; whether it finishes or not, STOP and report: packet id (full), branch, commit sha, gate packet id, files changed, tests added, and anything you observed that is worth a follow-up item (do NOT file items yourself). The operator resumes you if the gate goes red. Your report is recorded on your run's `reported` step once the gate is green; the run lands on it.
9. Do not: touch files outside your worktree; write to the jobs API except via `boss gate`; run kubectl mutations; read or print /etc/boss-train/forge.token or any credential; run a full `infra/gate.sh` (only the pre-flight door quoted in rule 4); start background tasks.
10. Web work in a worktree: the worktree has no node_modules, and `wt-web` (on PATH, the web half of wt-cargo) links the operator checkout's three — `node_modules`, `apps/web/node_modules`, `libs/web-kit/node_modules`, all gitignored — then runs the command you give it. `bun test src/…` works without them for most files. Then run WHAT THE GATE RUNS, once, before pushing: write `cd <your worktree>/apps/web && bun run test:unit && bun run build && bun run test:mocked` into `web.sh` in your scratch dir (rule 0) and run `wt-web bash <your scratch dir>/web.sh > <your scratch dir>/web.log 2>&1` from the worktree — the script's chain is the gate's web-suite phase verbatim (the pin `builder_rules_name_the_gates_web_suite` holds this list to `infra/gate.sh`). `bun test src/` is only the first of those three: the mocked specs live in `apps/web/tests/mocked/` and nothing under `src/` reaches them — on 2026-09-22 a car's first gate went red on six checks, five of them mocked specs, and that one command takes about two minutes (backlog 3566f5b4).
11. Svelte 5: never name a prop or local `state`, `derived`, `effect` or `props` — it shadows the rune and svelte-check reports a store misuse three lines from the cause (cost a builder 2 min on 2026-09-15).
12. Shell under `set -o pipefail`: never `… | head` or `… | grep -q` with a producer that keeps writing — SIGPIPE makes a random red (the no-producer-coin pin refuses it; it caught four lines in one builder's first draft, 2026-09-18). Make `head`/`grep` the producer or drain the pipe with `tr`/`cat`.
13. Keep the change small and the diff only your files. Match the surrounding comment density and voice (comments say WHY with dates and packet ids, as the codebase does).
14. Read which FUNCTION a cited line sits in before you change it. A packet's line number is a lead, not a measurement — it drifts, and a pattern grep mis-targets. Measured 2026-09-20 in `sensor_poll.rs`: the same `.get("data") … unwrap_or_default()` chain appeared four times, of which one was the real defect, one was a second live defect, one was SAFE BY ACCIDENT of the truncation check right after it, and one was a different shape. Two packets that day cited a line inside the guarded function (6c4c432a, then 0767c830 whose line had drifted 823→818). Open the function, not the line.
15. Verify the packet's PREMISE, not only whether its fix already landed. `boss dispatch` refuses a packet a merged car already covers (a7837d81); nothing can refuse a packet whose claim was never true. REFUSING TO BUILD IS A GOOD OUTCOME and the report is the deliverable: on 2026-09-20 packet ef74fc12 said the jobs API had no version endpoint, and `/api/jobs/health` had returned the build commit since the initial commit three months earlier, with `boss running` already reading it — the three paths the packet measured were simply not the `/api/<prefix>/health` convention 24 services follow. Say so, name the evidence, build nothing.
16. The pre-flight door — check its EXIT CODE, not its last line. Reading it for a closing word invites `| tail`, and a pipeline hides the failure: on 2026-09-20 the operator piped the pre-flight through `tail -2` and chained the commit and the push behind the pipeline's `&&`; the gate FAILED, `tail` succeeded, and the `&&` chain pushed anyway. Redirect to a file, read the exit status, then print the file. (The redirect form is the invariant's own first line, quoted under rule 4.) Run it as ONE PLAIN COMMAND and read the status the tool reports: a worktree-isolated session's harness refuses `bash ... > log 2>&1; echo $?` as too complex to verify, while the same command without the `; echo $?` runs and the tool reports its exit code (measured on run dba4bb17, 2026-09-23; backlog 65cea113).
17. Never `git checkout origin/main -- .` in your worktree. Rule 1 forbids rebase, force-push and `reset --soft`; this is the fourth way to lose your own work, and a builder reached for it on 2026-09-20 while rehearsing a probe against main — it reverted and staged the whole working tree (caught, restored, commit already made). To READ another revision use `git show origin/main:<path>`, which cannot write.
18. COMMIT before you run the touched crate's whole suite. `boss-testing::gate_sh::the_receipt_times_every_check` fails on any UNTRACKED file — correct, because the gate checks out the PUSHED commit — so rule 4's suite gives a FALSE answer before the commit, and the failure is indistinguishable from a real one. It cost a builder one ten-minute suite run on 2026-09-20 (26a856d4), on its own uncommitted migration.
19. A recorded probe, four rules, each paid for on 2026-09-20. (a) Date any cutoff from `$BOSS_CAR_CONVERGED_AT`, never `git log -1 --format=%ct HEAD`: HEAD moves with every train (~40 min) while the event you wait for may be weekly, so the window resets faster than the event can land — car ead4a6ed starved two days that way. (b) Never count a list read with a bare `limit=` without comparing rows to `.total`: measured, 33 of 49 recorded probes do exactly that (e7cf78c6), and one had its single qualifying row in the unread tail of a 300-of-345 page. (c) Grep `pub fn <name>` or `pub const <NAME>`, never a bare name — a doc comment defeated a probe by matching the mention instead of the definition. (d) Rehearse BOTH legs before launching, including a negative control against `origin/main`: a probe that cannot fail on unconverged main proves nothing.
