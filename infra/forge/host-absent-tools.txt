# WHAT ELSE `boss gate --park-probe` REFUSES, and why it is here: this
# file is where the gate's refusals send a builder, so the other one
# should be readable in the same place.
#
# A probe that reads the system of record with curl/wget/python and NO
# identity is refused. Backlog 61085a9e, measured 2026-09-10 on one
# backend at one commit: an unidentified reader is answered with a
# NARROWER WORLD, silently — ?kind=ship-a-change&status=open was 21
# rows for the operator and 0 unidentified, and /api/yard/status came
# back with trains, dock, held, recent and dock_depth ALL ZERO: a
# confident, well-formed, completely idle yard. /api/workflows was
# identical for both readers, so nothing in an answer says which kind
# you hit.
#
# A PRESENCE assertion then fails for the wrong reason, which someone
# investigates. An ABSENCE assertion PASSES FALSELY, and
# the unattended door records it as a proof on a car that closes. So
# prefer asserting the presence of a NAMED thing over the absence of
# any thing — a count-is-zero or flag-is-false claim against a
# policy-scoped surface is exactly what a narrowed read produces.
#
# Read it as a named reader instead. This one is IN THE TREE, so the
# converged checkout has it with no install step, and
# the unattended door puts it first on the probe's PATH:
#
#   boss-sor-read /api/yard/status | grep -q '"dock_depth":1'
#
# It is GET-only (no method argument exists), the base comes from the
# runner, and the identity is a read-scoped actor the runner exports —
# `audit-readonly`, which core policy grants Read at Scope::All on
# every shipped resource and no other action anywhere. Verified by
# effect against the live deployment: a metadata PATCH and a step PUT
# with that actor both answered 403 "no active rule for role
# audit-readonly on job:update" / "…on step:update".
#
# `curl -fsS -H "x-boss-user: $BOSS_SOR_USER" $BOSS_JOBS_URL/api/...`
# is accepted too — the refusal is about reading UNIDENTIFIED, not
# about curl.
#
# THREE THINGS IT DOES NOT REFUSE, narrowed 2026-09-11 (backlog
# 5dc5159d) after nine correct probes had to argue past it — four of
# them in one afternoon, which makes the override routine, and a
# routine override is read by nobody:
#
#   - A READER PIPED INTO A PARSER. `boss-sor-read /api/... | jq -e ...`
#     or `| python3 -c ...`: the reader does the read, the parser is
#     handed its stdout. `python3` is still a client when the text
#     names something that could open a socket (urllib, requests,
#     http.client, socket, subprocess, …) — which is the first
#     measured instance, `urllib.request.urlopen`.
#   - A GATEWAY SESSION. `POST /api/auth/guest`, then `curl -b` with
#     the cookie it returned. Measured the same day: that session read
#     22 / 56 / 703 rows where the operator's own door read 22 / 56 /
#     703 and an unidentified read of the jobs API's own port read
#     0 / 0 / 0. A FORGED cookie literal answers 401, identical to
#     sending none — so unlike a header, a session cannot be
#     self-asserted, and admitting it cannot produce a false pass.
#     It counts only for a gateway-shaped read: a cookie says nothing
#     about a read on :7900, which does not read cookies.
#   - Nothing else. A route-SHAPE probe (401-vs-404 with a control
#     that fails closed) is still refused and still needs
#     `--probe-anyway`: what makes it safe is its control, which is
#     program logic, not something a text scan can see.
